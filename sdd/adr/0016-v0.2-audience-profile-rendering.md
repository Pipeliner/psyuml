# ADR-0016: v0.2 M13 — audience-profile rendering + the render() dispatcher

- **Status:** accepted
- **Date:** 2026-06-15
- **Deciders:** project owner + maintainer
- **Spec / REQ touched:** v0.2 §2, §3, §8 / REQ-AUDIENCE-PROFILES, REQ-EDITOR-MVP, REQ-ACCESSIBILITY (extends ADR-0014)

## Context
M11 shipped the audience-profile *registry* (`AUDIENCE_PROFILES`: clinician / client / picture,
each with `plainLanguage` / `showInterpretive` / `maxSymbolKinds`). M13 turns it into real
rendered output + an editor surface. The spec (v0.2 §2) says each family `SHOULD` offer the three
profiles, **sharing identical semantics** but differing in *visual compression*, and that profiles
`MUST NOT` change the model — only its rendering.

Forces / constraints:
- v0.1 already threads `layer: 'clinician' | 'client'` through every renderer; the audience
  profile is a higher-level selector that should *drive* the layer, not duplicate it.
- The render dispatch was **duplicated** — an if-chain in `apps/web/App.tsx` and a `RENDERERS`
  map in the CLI — with no shared entry point to host audience resolution.
- M12 added a clinician-analytic surface to the Pattern renderer (contested ⚖, as-if, confidence,
  provenance); ADR-0007 added cross-school provenance to the Parts renderer. The client/picture
  profiles must be able to *hide* that surface — without churning the v0.1 goldens.
- The overlap invariant (ADR-0012) and all goldens must stay green.

## Decision
1. **Add a single `render(model, options)` dispatcher** in `@psyuml/render` — the one entry point
   the editor uses. It resolves the **audience profile → effective `layer` + `showInterpretive`**
   once, then dispatches by `model.diagram`. An explicit `layer` / `showInterpretive` still wins,
   so existing `layer`-only callers (CLI `RENDERERS` map, the golden tests) are byte-unchanged.
2. **`audience` resolution:** clinician → clinician labels + `showInterpretive: true`; client /
   picture → client labels + `showInterpretive: false`. Resolution lives in the dispatcher (not in
   each renderer): keeps the 10 non-analytic renderers untouched; the contract is "pass `audience`
   to `render()`, pass `layer` to a direct renderer".
3. **Gate the analytic surface on `showInterpretive`** in the two renderers that have one —
   `renderLoopMap` (M12: contested ⚖, as-if, the standing/confidence alt-text lines) and
   `renderPartsMap` (ADR-0007: provenance tags + the contested-origin ⚖ + "Origins disagree"
   alt-text). Defaults to `true`, so clinician / `layer`-only output is unchanged (no golden churn).
   The **descriptive-vs-interpretive dashed border stays in every profile** — it is a §3 MUST and
   is honest, jargon-free de-emphasis (good for clients), not clinician-only meta.
4. **Editor (`apps/web`):** the diagram picker is **grouped by family** (`<optgroup>` per
   `listFamilies()`), an **Audience** selector replaces the old clinician/client Layer toggle (the
   `layer` used by validate/diff is derived from it), and rendering goes through `render()`. Export
   inherits the active profile because it serializes the rendered SVG / alt-text.
5. **Symbol-budget = a nudge, not a block:** `@psyuml/profiles.withinSymbolBudget(kinds, audience)`
   (clinician = no cap; client = 6; picture = 5); the editor shows a gentle over-budget note. The
   real reduction (pictographic, fewer kinds) is the comprehension-tested M14 work.

## Consequences
- **Positive:** one audience switch drives label language + analytic visibility coherently; the
  duplicated dispatch is replaced by a shared, tested `render()`; a client/picture view is plain
  (no "school:cat" tags, no ⚖/as-if/confidence) while staying structurally honest (loop, topology,
  dashed tentativeness, exits). Zero golden / overlap churn — defaults preserve v0.1 + clinician.
- **Negative / cost:** the CLI still keeps its own `RENDERERS` map (not yet refactored onto
  `render()`) — minor duplication, deferred. `showInterpretive` gating is wired only in the two
  renderers that actually have an analytic surface; if a future renderer adds one it must opt in.
  The symbol budget is advisory only; picture is currently "client + a flag" until M14 supplies
  pictographic, comprehension-tested symbols. The editor UI itself remains unit-untested (logic is).
- **Impact:** `packages/render/index.ts` (+ test), `packages/profiles/index.ts` (+ test),
  `apps/web/App.tsx`; traceability REQ-AUDIENCE-PROFILES (impl extended). See
  `packages/render/IMPACT.md`, `packages/profiles/IMPACT.md`, `apps/web/IMPACT.md`.

## Alternatives considered
- **Resolve audience inside every renderer** (a shared `resolveLayer`/`resolveShowInterpretive`
  in all 12). Rejected for M13 — 12 mechanical edits + risk, for renderers that don't read
  `showInterpretive`; the dispatcher is the natural single resolution point.
- **Hide the dashed interpretive border in the client view too.** Rejected — §3 makes the
  descriptive-vs-interpretive distinction a MUST, and "this is our best guess" (dashed) is honest,
  plain-language de-emphasis a client benefits from; what we hide is the clinician *jargon*.
- **Auto-reduce symbol kinds to fit the picture budget now.** Rejected — that is the M14
  participatory + comprehension-tested pictographic work; silently dropping symbols would be both
  lossy and unvalidated. A nudge is the honest M13 step.
- **Route the budget through `@psyuml/validate`.** Rejected — would add a validate→profiles
  dependency between siblings; the editor already imports profiles, so the nudge lives there.
